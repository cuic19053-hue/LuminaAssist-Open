# 光语助手（LuminaAssist）用户体验报告

> **评估版本**：2026-07-23 代码快照（commit `0728fbc`）
> **评估范围**：端侧 ArkTS + 后端 FastAPI 全栈
> **评估方法论**：启发式评估（Nielsen's 10 Heuristics）+ WCAG 2.1 AA/AAA 对标 + VUI 专项检查

---

## 一、执行摘要

光语助手（LuminaAssist）是一款定位精准、架构扎实的**视障与高龄用户多模态智能助理**。项目以"零界面门槛 / 全语音控制 / 全场景视觉代偿"为核心理念，在 HarmonyOS 5.0 (API 12) 平台上实现了端云双态视觉识别、药品结构化分析、TTS 全链路语音反馈、紧急通讯等核心功能。

**核心结论**：产品在无障碍设计规范和架构工程方面表现**优秀（85/100）**，但在语音输入（ASR）、端侧 OCR、多轮对话等关键用户路径上存在**明显缺口**，当前处于 **MVP 早期阶段**，尚未达到可交付视障用户日常使用的完整度。预计完成 P1-P2 优先级特性后，可达**商业可用水准**。

## 三、核心体验路径评估

### 3.1 主路径：全屏点击 → 拍照识别 → 语音反馈

这是当前产品**唯一完整的端到端用户路径**，评估如下：

```
用户点击屏幕任意位置
    ↓ [振动 200ms + TTS "正在拍照，请保持稳定"]
    ↓ [200ms 内完成]
后置摄像头静默拍摄单帧 JPEG
    ↓ [振动 200ms + TTS "已拍好，正在识别"]
    ↓ [1-5 秒，取决于端侧/云端路径]
分类结果 → TTS 朗读
    ↓ [如 "画面中可能包含：金毛犬(92.3%)、拉布拉多(5.1%)"]
状态恢复为"点击屏幕任意位置开始识别"
```

**体验评分**：

| 维度 | 评分 | 说明 |
|---|---|---|
| 可发现性 | ⭐⭐⭐⭐⭐ | 整屏可点击 + 底部永久提示条，零学习成本 |
| 操作效率 | ⭐⭐⭐⭐⭐ | 一次点击完成全流程，无需多步操作 |
| 反馈及时性 | ⭐⭐⭐⭐ | 三阶段语音+振动反馈，每阶段 < 200ms 延迟 |
| 容错性 | ⭐⭐⭐⭐ | 拍照失败/识别失败均有中文 TTS 提示 + 重试引导 |
| 隐私安全感 | ⭐⭐⭐⭐⭐ | 阅后即焚、不落盘、无预览 UI、不打印 base64 内容 |

**关键发现**：

- ✅ **静默拍照设计**非常出色——视障用户无需"对准"，后台自动拍摄，大大降低了使用门槛
- ✅ **振动+语音双通道反馈**符合视障用户感知习惯：振动表"拍好了"，语音表"识别结果"
- ⚠️ **缺乏拍照引导**：当前实现无法告知用户"再靠近一点""光线太暗"等拍摄质量反馈
- ⚠️ **MobileNetV2 1001 类局限**：仅能识别 ImageNet 类别（动物/日常物品），无法覆盖药品、菜单、路牌、钞票等视障用户真正需要的细粒度场景

### 3.2 药品识别路径（差异化亮点）

```
用户说"这是什么药" → 后端 Agent 规划 → 端侧执行
    ↓ [{action:"capture_image"}, {action:"medicine_recognition"}]
拍照取帧 → VisionService.recognizeMedicine()
    ↓ LLM 返回结构化 JSON（药名/用法/禁忌/有效期/风险等级）
    ↓ 解析 JSON → 口语化 TTS 文案 + 风险振动
用户追问："一次吃几粒？"
    ↓ [{action:"medicine_qa", content:"一次吃几粒"}]
VisionService.answerMedicineQuestion() → 基于缓存 MedicineInfo + LLM 生成回答
```

**体验评分**：

| 维度 | 评分 | 说明 |
|---|---|---|
| 信息架构 | ⭐⭐⭐⭐⭐ | 结构化抽取 9 项字段（名称/规格/用法/适应症/禁忌/不良反应/有效期/厂家/风险等级），覆盖视障用户全部关切 |
| TTS 文案质量 | ⭐⭐⭐⭐⭐ | System Prompt 精心设计：用"您"、白话解释、强调语气、过期警告、总结提示——非常贴近真实药师的口吻 |
| 安全设计 | ⭐⭐⭐⭐⭐ | 风险等级 0/1/2 + riskHint 字段 + 高风险 600ms 长振动——多模态风险传递 |
| 追问能力 | ⭐⭐⭐⭐ | 基于缓存信息+LLM，无需重新拍照，自然语言理解 |
| 边界处理 | ⭐⭐⭐⭐ | JSON 解析失败→降级纯文本兜底；无缓存→引导先拍照；模糊图片→重新对准提示 |

**关键发现**：

- ✅ 这是产品**最具差异化竞争力**的功能——市面上尚无面向视障用户的药品专用深度识别方案
- ✅ System Prompt 中对 TTS 文案的要求（"用您代替你""白话解释""千万不能"等）体现了对老年用户的深刻洞察
- ⚠️ 当前仅支持单药品识别——若画面中有多盒药，LLM 可能只识别最显眼的一盒
- ⚠️ MedicineInfo 缓存仅在内存中，App 重启后丢失，无法做"上次您看的是阿莫西林"的跨会话记忆

### 3.3 语音输入路径（缺失）

**当前状态**：

```typescript
// ASRService.ets / SpeechService.ets
public startASR(onResult, onError): void {
  this.asrReady = false;
  onError('语音识别不可用：当前 OpenHarmony SDK 不含 speechRecognizer 模块。请改用文本输入。');
}
```

**影响评估**：🔴 **严重**

- 产品核心理念是"全语音控制"，但用户**根本没法用语音输入指令**
- 主页面（Index.ets）没有任何文本输入框——用户完全无法发起 Agent 任务规划（叫车/发短信/紧急呼叫等复杂指令）
- 这导致 `Agent.invoke()` → `IntentRouter.route()` → 后端 `/api/v1/agent/plan` 这条完整链路**在端侧无触发入口**
- 当前实际可用的只有"全屏点击→拍照识别"这一条路径

### 3.4 多轮对话与上下文记忆

| 特性 | 当前实现 | 理想状态 |
|---|---|---|
| 会话历史 | `Agent.sessionHistory` 内存中 Map，最多 20 轮 | ✅ 基本满足 |
| 药品追问上下文 | `VisionService.lastMedicineInfo` 内存中单个缓存 | ⚠️ 仅支持最近一次药品 |
| 跨会话记忆 | ❌ 未实现 | 用户期望"上次你帮我识别的那盒药" |
| 用户偏好学习 | ❌ 未实现 | 如"用户对青霉素过敏"长期记忆 |

## 六、技术架构与性能

### 6.1 架构质量

| 维度 | 评分 | 说明 |
|---|---|---|
| 前后端分离 | ⭐⭐⭐⭐⭐ | 端侧不持有 Prompt/API Key（通过 KeyStore 加密注入），后端统一管理 |
| 三层架构 | ⭐⭐⭐⭐⭐ | agent/ → services/ → utils/ 单向依赖，无循环引用 |
| 单例模式 | ⭐⭐⭐⭐⭐ | 7 个核心类全部单例，全局一致性有保证 |
| 优雅降级 | ⭐⭐⭐⭐ | 端侧→云端自动回退；TTS 失败→振动兜底；JSON 解析失败→纯文本降级 |
| 代码质量 | ⭐⭐⭐⭐ | 注释详尽，中文 Error 一致，每个方法有 JSDoc |

### 6.2 性能特征

| 路径 | 预估延迟 | 网络要求 |
|---|---|---|
| 端侧 MobileNetV2 分类 | **50-200ms**（NPU）/ 200-800ms（CPU） | 无 |
| 云端 Qwen-VL 识别 | **1-5 秒** | 需要 |
| TTS 合成+播放 | **1-3 秒**（含网络+合成+下载+播放） | 需要 |
| 后端 Agent 规划 | **0.5-2 秒** | 需要 |
| 端到端（端侧路径） | **~2 秒** | 需要（TTS 仍需网络） |
| 端到端（云端路径） | **~5-10 秒** | 需要 |

**关键发现**：

- TTS 依赖云端 DashScope（cosyvoice-v3-flash），这导致**即使端侧分类可用，完全离线仍不可行**
- 如果用户未配置网络或 API Key，仅能获得振动反馈，无语音播报——对全盲用户来说这是一个严重降级
- 建议：增加本地 TTS 引擎（利用 HarmonyOS 系统 TTS）作为离线兜底

### 6.3 隐私安全

| 检查项 | 实现 | 评分 |
|---|---|---|
| API Key 硬编码 | ❌ 发现硬编码测试 Key（`EntryAbility.ets:143` `sk-your-test-key-placeholder...`） | 🔴 |
| 图像数据落盘 | ✅ 阅后即焚，不持久化 | ✅ |
| 日志泄露 | ✅ 不打印 base64/API Key 内容 | ✅ |
| KeyStore 加密 | ✅ HUKS + Preferences 加密存储 | ✅ |
| 网络传输加密 | ✅ HTTPS + Bearer Token | ✅ |

> ⚠️ **高风险发现**：`EntryAbility.ets` 第 143 行存在硬编码的测试 API Key `sk-your-test-key-placeholder`。虽然标注为"测试模式"，但代码位于生产入口文件中，一旦提交到公开仓库即造成 Key 泄露。**建议立即移除，改为 .env / 构建参数注入。**

## 七、用户体验优势与亮点

### 7.1 核心竞争力

1. **💊 药品专用深度识别**
   - 市场上尚无面向视障用户的药品识别专用方案
   - 结构化 9 项字段 + 风险等级 + 振动强提醒 + 口语化 TTS + 追问能力
   - System Prompt 设计体现了对老年用户的深刻理解（"用您""白话解释""千万不能"）
   - **可直接作为 B2B 差异化卖点向养老院/残联推广**

2. **📱 极简交互范式**
   - "点击任意位置即识别"——对全盲用户来说，这是唯一真正可行的交互方式
   - 不需要找到按钮、不需要对准摄像头、不需要理解 UI 布局
   - 这是同类产品中少有的"真正为盲人设计"而非"为明眼人加无障碍标签"

3. **🏗️ 端云双态架构**
   - 端侧 MobileNetV2 毫秒级响应（离线场景兜底）
   - 云端 Qwen-VL 强大理解能力（复杂场景）
   - 架构天生支持"数据不出设备"的政府采购硬性要求
   - 为后续端侧大模型（HarmonyOS 6+ aiEngine）预留了接口

4. **🛡️ 全链路 TTS 兜底**
   - 没有任何一个错误是"静默"的
   - 每个 try-catch 都有 `accessibility.speak()`
   - TTS 失败自动降级振动——视障用户永远不会面对"黑屏无声"

## 八、关键问题与风险

### 8.1 🔴 阻塞性问题（P0）

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **ASR 语音输入完全缺失** | 产品"全语音控制"定位落空；Agent 任务规划链路（叫车/短信/紧急）在端侧无触发入口 | 接入第三方 ASR（如阿里云实时语音识别），或将 DashScope Paraformer 集成到端侧；短期可加文本输入框作为兜底 |

### 8.2 🟡 重要问题（P1）

| # | 问题 | 影响 | 建议 |
|---|---|---|---|

## 十二、总结

光语助手是一个**方向极其正确、架构功底扎实、但功能尚不完整**的早期 MVP 产品。

**最值得肯定的三点**：

1. **无障碍设计不是"附加"而是"原生"**——从交互范式（整屏点击）、信息通道（TTS+振动）、容错设计（全链路兜底）到 System Prompt 措辞（"用您""千万不能"），每个细节都体现了"为视障与高龄用户设计"而非"为明眼人加无障碍标签"。
2. **药品专用识别是一个真正的差异化武器**——结构化 9 项字段 + 风险等级 + 口语化播报 + 追问，这个功能在国产同类产品中是先行者。
3. **端云双态架构为商业落地预留了空间**——离线能力支撑政府采购/老人机预装，云端能力支撑订阅服务，架构层面已经想清楚了。

**最需要立即改进的三点**：

1. **语音输入**——产品叫"光语助手"但用户还不能"语"，这是最大的体验断裂点
2. **硬编码 Key**——安全红线，必须立即处理
3. **真机验证**——架构再漂亮，没过真机测试就是空中楼阁
