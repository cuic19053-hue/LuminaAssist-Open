## 阶段 2：OCR 转换链路验证（convert_models.sh ocr）— 已完成 ✅

### 执行记录（2026-08-31，日志 `build/convert_ocr.log`）
最终验证通过的转换链路：
```
PP-OCRv3 FP32 标准版 (BOS)
  → paddle2onnx 1.2.4 + paddlepaddle 2.6.2 → ONNX opset13（中间产物保留于 model_workspace/ppocrv3_{det,rec}.onnx）
  → converter_lite 2.1.0 --fp16=on --saveType=MINDIR_LITE → .ms
```
产物（已放置 `entry/src/main/resources/rawfile/models/`）：
| 文件 | 体积 | 输入 shape | benchmark（x86 2线程） |
|---|---|---|---|
| paddle_ocr_det_fp16.ms | 1.2MB | [1,3,320,320] | AvgRunTime 6.74ms ✅ |
| paddle_ocr_rec_fp16.ms | 5.3MB | [1,3,48,320] | AvgRunTime 6.73ms ✅ |

引擎侧兼容性：`LocalOCREngine.runRec` 已自适应输出布局（[seq,class]/[1,seq,class]/[seq,1,class]）；
batch=1 时输入元素总数与无 batch 假设一致（3×48×320=46080 floats），预处理无需改动。

### 问题清单
| # | 问题 | 根因 | 解决 |
|---|---|---|---|
| P2-1 | paddle2onnx 报 unsupported operators（fake_channel_wise_quantize_dequantize_abs_max 等）转换 abort | PP-OCRv3 **slim 量化版**模型内嵌量化算子，paddle2onnx 不支持 | 改用官方 BOS 的 **FP32 标准版** `ch_PP-OCRv3_{det,rec}_infer.tar`（已更新 get_model_weights.ps1） |
| P2-2 | converter_lite INT8 权重量化失败：`GetConvChannel not find node: conv2d_x.w_0` + `InferShape failed (Conv2DFusion)` | converter 2.1.0 WeightQuant 对该 ONNX 的权重解析失败 | 放弃 INT8，改为 **FP16 直转**（体积 det 1.2MB / rec 5.3MB，可接受；benchmark 验证通过） |
| P2-3 | rec 转换失败：`InferShape failed, name: p2o.Conv.0` | rec 输入形状误设为 3 维 `[3,48,320]`，Conv 需要 4 维 NCHW | 改为 `[1,3,48,320]`（已修正 convert_models.sh 并注释） |
| P2-4 | benchmark 报 `LoadMindIR ParseFromArray failed` | MSL2 flatbuffer 与 unified benchmark 默认 MindIR 解析路径不匹配 | 用默认 MindIR 格式副本完成 benchmark 数值验证（det/rec 均 Success），端侧交付格式仍为 MINDIR_LITE |
| P2-5 | WSL NAT localhost 代理告警 | 已知环境噪声 | 忽略，不影响转换 |

## 阶段 3：引擎改造（已完成）

### 3.1 LocalOCREngine（真实 OCR 管线）
- **改造前**：单文件模拟实现——预处理"省略归一化"，输出硬编码文案。
- **改造后**：det + rec 双模型全管线：
  ```
  base64 → PixelMap(原图≤960) → detPreprocess(320², CHW, (x/255-0.5)/0.5)
  → DBNet 概率图 → BFS 连通域文本框 → 坐标映射回原图 → 阅读顺序排序
  → 逐行裁剪(外扩2px) → recPreprocess(48×320) → CRNN → CTC 贪心解码 → 文本
  ```
- 关键文件：
  - [LocalOCREngine.ets](../LuminaApp/entry/src/main/ets/services/LocalOCREngine.ets)
  - [OcrPostprocess.ets](../LuminaApp/entry/src/main/ets/utils/OcrPostprocess.ets)（纯逻辑，可单测）
- 新增运行时资产：`paddle_ocr_det_fp16.ms` / `paddle_ocr_rec_fp16.ms` / `ppocr_keys_v1.txt`
- **命名变更说明**：原计划单文件 `paddle_ocr_lite_int8.ms` 不可行（PaddleOCR 检测/识别本就是两个模型），已按 det/rec 双文件命名；后因 slim 量化模型转换失败（P2-1/P2-2），最终交付 FP16 版并同步引擎常量与注释。

### 3.2 LocalSLMEngine（真实 LLM 管线）
- **改造前**：UTF-8 原文字节直接塞进模型输入（无分词），空输出即抛错。
- **改造后**：
  - 新增 [QwenTokenizer.ets](../LuminaApp/entry/src/main/ets/utils/QwenTokenizer.ets)：GPT-2 风格字节级 BPE
    （正则预切分 → bytes_to_unicode → merges 优先级合并 → vocab 查表；含 ChatML 模板拼接）；
  - init 时**自适应输入绑定**：探测 `getInputs()` 的 name/shape/dtype，按名称角色分为
    token_ids / attention_mask / position_ids / kv_cache，logits 输出按词表维度 151936 定位；
  - 贪心迭代解码（≤128 token，遇 `<|im_end|>`=151645 / `<|endoftext|>`=151643 停止）；
  - `planIntent()` 保留 JSON 提取容错；任何失败优雅降级（ready=false → OfflinePlanner 规则兜底）。
- 新增运行时资产：`qwen2_0_5b_int4.ms` / `qwen_vocab.json` / `qwen_merges.txt`（下载脚本自动放置）。

- **产物格式阻塞（当前问题）**：

    flatbuffer 32 位 offset 有 2GB 内联上限，**HarmonyOS `loadModelFromFile` 无法加载 .msw 组合**。
- **当前策略**：FP16 直转（`--fp16=on`）把权重存储减半至 ~1.3GB < 2GB 上限，期望产出单文件 .ms
  （执行中，日志 `build/qwen_fp16.log`）。成功则引擎改加载 `qwen2_0_5b_fp16.ms`。
