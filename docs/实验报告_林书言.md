# 光语助手系统实验报告

撰写人：林书言  
日期：2026 年 7 月 24 日  
课题：LuminaAssist（光语助手）功能验证实验  

---

## 1. 为什么做这次实验

我这次主要是把「光语助手」从头到尾跑通一遍，看它是不是真能按设计工作。具体想确认四件事：

第一，电脑上的 FastAPI 后端能不能起来，健康检查和任务规划接口是否正常；  
第二，手机上的鸿蒙 App 能不能把说话、拍照、听结果这条链路走完；  
第三，所谓「端云双态」——能在手机上做的分类尽量本地做，规划交给后端——实际用起来感不感觉得到；  
第四，面向视障用户的大按钮和语音提示，在真机上是否靠谱，出错时会不会“哑巴”。

和组里另一位同学做的是同一套实验内容，只是我按自己的记录习惯来写。

---

## 2. 我用的环境

- IDE：DevEco Studio 5.0 及以上  
- 系统：OpenHarmony 5.0，API 12  
- 设备：优先鸿蒙真机，模拟器只做联调参考  
- 后端：本机 Python 3.10+，FastAPI，监听 8000  
- 大模型：阿里云百炼（DashScope）  
- 本地模型：MindSpore Lite 加载的 MobileNetV2  
- 网络：手机和电脑连同一个 Wi‑Fi  

装环境和导入工程时，务必打开的是 `LuminaApp` 目录，而不是仓库根目录；这一点我第一次踩过坑。

---

## 3. 我怎么做的

### 3.1 先看后端

在 `backend` 里装好依赖，把 `.env.example` 拷成 `.env`，填好 `ALIYUN_API_KEY`，再 `python main.py`。  
然后用浏览器或 curl 打一下 `/health`。只要看到状态 ok、并且显示 Key 已配置，我就认为后端这一关过了。  
接着拿一句口语去调 `/api/v1/agent/plan`，例如「帮我看看眼前是什么」，看返回里有没有 `tasks` 和 `tts_message`。

### 3.2 再装端侧、做联调

DevEco 打开工程、配好 SDK 路径和自动签名，装到手机。设置页里后端地址我写成电脑的局域网 IP（例如 `http://192.168.x.x:8000`），没有用 localhost——真机访问不到本机回环地址。  

联调顺序我习惯是：先发一条**文字**指令（先排除语音识别干扰）→ 再试**长按说话** → 最后试**短按拍照识别**。

### 3.3 场景清单（与同组报告一致）

| 编号 | 我测的场景 | 怎么测 | 我盯什么 |
| --- | --- | --- | --- |
| E-01 | 健康检查 | 调 `/health` | 是否 ok、Key 是否配上 |
| E-02 | 任务规划 | 自然语言进 plan 接口 | tasks 和播报文本是否齐全 |
| E-03 | 读说明书 | 说「读一下说明书」并拍照 | 能不能读出字，会不会没声 |
| E-04 | 认眼前物体 | 「前面是什么」并拍照 | 有没有结果；弱网时本地分类是否还在 |
| E-05 | 认药 | 「这是什么药」+ 药盒 | 界面卡片和语音是否对得上 |
| E-06 | 随便问问 | 「今天星期几」 | 有没有回答；失败有没有提示 |
| E-07 | 故意连错后端 | 设置里写错地址 | 是否提示失败、会不会闪退 |
| E-08 | 关掉相机权限 | 拒绝权限后再点识别 | 有没有说明、是否稳住 |

## 4. 结果记录

| 编号 | 我的判定 | 当场感受 / 备注 |
| --- | --- | --- |
| E-01 | 通过 | 启动日志里能看到 Key configured，心里比较踏实 |
| E-02 | 通过 | plan 能吐出任务；播报文案可以直接拿去 TTS |
| E-03 | 通过 | 说明书拍清楚时，朗读基本可用 |
| E-04 | 通过 | 本地粗分类比较快；要细说画面时会等云端几秒 |
| E-05 | 通过 | 药品信息能出卡片，也能听 |
| E-06 | 通过 | 问答路径正常 |
| E-07 | 通过 | 连错地址时有失败提示，没有卡死或闪退 |
| E-08 | 通过 | 拒相机后有反馈，应用还在 |

另外三点我想单独记一下：

- 后端地址写成 `localhost` 时，百分之百会“网络失败”，改成局域网 IP 就好了。  
- 等云端视觉结果的那几秒，界面会停在思考状态，有语音预期的话用户还能接受。  
- 模拟器上看端侧加速没太大意义，有 NPU 的真机更有参考价值。

---

## 5. 我的一点看法

端侧做感知和执行、后端做理解和规划，这个分工我实际跑下来是说得通的：本地分类反应快，Key 和 Prompt 放后端也更安全、好改。  

整条链路最要紧的是「永远有声音」——成功要播，失败也要播。这次实验里错误兜底基本做到了。  

不过也要客观：有的端侧 OCR / 视觉大模型能力还在补齐，模型没就绪就走云端，这是设计上的降级，不是偶发 bug。药品相关内容也只能当辅助，不能当真处方。

---

## 6. 结论

按同一套用例测下来，后端、端侧联调以及阅读 / 认物 / 看药 / 问答等主场景都可以完成；端云双态和无障碍反馈达到了我对本次实验的预期。若还要写进正式测评材料，建议再补一些真机上的耗时和识别准确率数据，会更有说服力。
